Menu overhaul: how the shell looks

Conceptual frames for menu-overhaul-and-mouse-support-proposal.md. Chrome is drawn in the window over the visualiser. Labels follow the current panel; shortcuts and values are illustrative. Yellow is keyboard focus. A blue bar is the navigator selection, which stays put when focus moves to the inspector.

Where things go commands, objects, and fields split apart

Menu bar

  • Actions and jumps, not every parameter.
  • File, Project, Layers, Render, Timeline, Settings, Help.
  • Items call the command registry. Shortcuts match the labels.

Navigator

  • Shallow objects: Settings, Project, Render, Layers, Song markers.
  • Selecting a node sets the inspector root.
  • Value rows do not appear in this column.

Inspector

  • Fields for the current selection only.
  • Collapsible groups stay inside this column.
  • Same row descriptors and mutations as today.

  5. 5

  7. 7
    Splitters. Hit rects exist from the first layout pass. Drag to resize lands in the mouse phase.

2. Same chrome, four selections the inspector swaps; the navigator stays shallow

Each frame is the same window. Only the selected node, the inspector groups, and whether the timeline strip is open change.

3. Menu taxonomy green runs a command, plain text jumps to a navigator root, grey is disabled

Render, separate, and backup started from a menu still use the in-window loading screen. Help lists commands grouped by these menus.
